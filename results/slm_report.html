Can small models act as permission gatekeepers for AI agents in Moodle?

Updated pilot report · Google Colab · 12 October 2026 · Based on the original pilot summary and the new colab_pilot.ipynb PDF output.

The new run strengthens one finding: the 7B Qwen model is the strongest zero-shot baseline, reaching 72.5% matched-pair accuracy. But neither fine-tuning Qwen on WebGuard data nor evaluating PolicyGuard-4B solved the context-sensitive permission task. No tested model reaches the project's 80% pair-accuracy gate.

  • Pair accuracy remains the key metric. A model must get both sides of a matched pair right—BLOCK the disallowed action and ALLOW the permitted counterpart. Ordinary item accuracy can hide failure to respond to changed context.
  • Scale helped in the zero-shot Qwen family, but not monotonically. Qwen 7B led at 72.5% pair accuracy; Qwen 1.5B reached 37.5%, while Qwen 0.5B and 3B scored 22.5% and 17.5%.
  • The fine-tuned WebGuard model did not transfer to this task. After QLoRA fine-tuning on 1,982 WebGuard training samples, Qwen-3B reached 43.8% item accuracy but 0% pair accuracy on the Moodle cases.
  • PolicyGuard-4B was also weak on matched pairs. It scored 56.2% item accuracy and 12.5% pair accuracy in this run.
  • Provisional decision: continue, but do not claim deployment readiness. Results support the motivation for a context-aware gatekeeper, while showing that more training data alone—or reusing an existing guardrail checkpoint—is not yet enough.

Goal and hypothesis

The project proposes an AI assistant inside a university learning platform such as Moodle or Canvas. Before the assistant executes a browser action, a small local gatekeeper checks whether that action is permitted by the user's role, the current platform state, and the course policy. Its decision can be ALLOW, BLOCK, or ASK.

The central research problem is context-sensitive authorization, not generic harmful-content detection. The same action may be allowed in a practice quiz and forbidden in a graded quiz, or allowed for a student's own record but forbidden for a classmate's private data. The model must notice the context fact that changes the correct decision.

Hypothesis under testExisting general-purpose and safety guard models will miss a meaningful share of these permission flips; a task-specific gatekeeper may improve reliability. The pilot tests the baseline and evaluation method, not a production-ready system.

Original methodology

Evaluation set
80 Moodle LMS test cases arranged as 40 matched pairs. The PDF reports that the cases were loaded from data/dummy/dummy_cases.json.
Pair construction
Within each pair, one contextual fact changes and the correct decision should flip. The original report describes 8 templates (T1–T8), with 5 pairs per template.
Case context
User role, request, page title and accessibility-tree snapshot, proposed action, Moodle state facts, and course-policy text.
Gold decisions
Each pair contains one disallowed and one allowed action. The intended pattern is BLOCK → ALLOW.
Evaluation flow
Load and validate the cases; run each adapter; map its native output to the common ALLOW/BLOCK label where needed; calculate item and pair metrics; compare models.
Runtime
Google Colab with a Tesla T4 GPU, reported as 15.64 GB VRAM. Models were evaluated sequentially and unloaded after each run.

Metrics and how to interpret them

  • Item accuracy: correctly labelled individual cases divided by 80.
  • Pair accuracy: pairs for which both cases are correct divided by 40. This is the primary context-sensitivity metric.
  • Flip rate: in this notebook's output, the reported flip rate equals pair accuracy because the gold label flips in every pair. It is not an independent metric.
  • Chance reference: the original report uses 25% as the approximate pair-accuracy reference for random independent guessing. A constant decision such as always BLOCK gives 50% item accuracy but 0% pair accuracy.
  • Decision gate: the project uses 80% pair accuracy as a practical threshold for this pilot; the original proposal's pivot condition also asks whether a strong full-context baseline approaches 95% or more.

What changed in the new run

The new Colab notebook expands the evaluation in two important ways beyond the earlier zero-shot comparison: it fine-tunes Qwen-3B on the official WebGuard training data using QLoRA, and it evaluates the actual Rakancorle1/PolicyGuard-4B checkpoint using its native output format.

  • Zero-shot Qwen baselines: Qwen2.5-0.5B, 1.5B, 3B, and 7B. The 7B model was loaded in 4-bit quantization; the other listed configurations used load_in_4bit=False.
  • WebGuard training data: the notebook downloaded the accessibility-tree training file containing 1,982 samples. Its reported labels were SAFE: 545, LOW: 876, HIGH: 561.
  • Fine-tuning: Qwen2.5-3B-Instruct was fine-tuned for 2 epochs with 4-bit QLoRA; the LoRA adapter was saved under models/webguard_qwen_lora.
  • Two-stage decision mapping: WebGuard's native risk tier was mapped as SAFE/LOW → ALLOW and HIGH → BLOCK. PolicyGuard's native no_violation → ALLOW and violation → BLOCK.
  • PolicyGuard-4B: loaded from Rakancorle1/PolicyGuard-4B and evaluated on the same 80-case set.

Insights gained from the new test

1. Larger Qwen models show a clearer ability to use context, but the trend is not smooth

Pair accuracy rises from 22.5% (0.5B) to 37.5% (1.5B), falls to 17.5% (3B), and then rises to 72.5% (7B). The 7B model is the clear best baseline in this run, but the 3B result means we cannot claim that performance improves steadily with parameter count. With only 40 pairs, each pair changes the score by 2.5 percentage points, so these results are preliminary.

2. High item accuracy is not proof of permission reasoning

Qwen-0.5B has 60.0% item accuracy but only 22.5% pair accuracy. PolicyGuard-4B has 56.2% item accuracy and only 12.5% pair accuracy. These gaps suggest that many individually plausible labels do not translate into correctly handling both sides of a context flip.

3. WebGuard's safety labels did not transfer to Moodle authorization

The fine-tuned model predicted a native WebGuard risk tier and then mapped that tier to ALLOW/BLOCK. It achieved 43.8% item accuracy but 0% pair accuracy. The sample output shown in the PDF predicts native SAFE, mapped to ALLOW, when the gold label is BLOCK. This is a concrete example of a risk classifier's label scheme not necessarily matching a platform's permission policy.

This result does not establish that WebGuard is ineffective at its intended web-action risk task. It shows that this particular fine-tuned Qwen adapter, training setup and deterministic label mapping did not solve the Moodle matched-pair task.

4. PolicyGuard's native violation decision also misses context flips

PolicyGuard-4B was loaded as the named checkpoint and evaluated through its native violation/no_violation format. Its pair accuracy was 12.5%. The sample output in the PDF says no violation → ALLOW for a case whose gold label is BLOCK. This is evidence of poor transfer to this test setup, not a general evaluation of all PolicyGuard use cases.

5. The gatekeeper hypothesis remains plausible, but the next experiment must isolate why models fail

The results are consistent with a gap between general safety classification and context-sensitive authorization. They do not yet prove that a newly trained gatekeeper will outperform these baselines. The next study should inspect raw outputs, verify input formatting, measure false allows separately from false blocks, and test a larger, more varied matched-pair dataset.

Limitations and validity checks

What these results do and do not establish
  • Small test set: 40 matched pairs across 8 templates gives only 5 pairs per template. Treat differences as pilot evidence, not definitive rankings.
  • Training/evaluation domain mismatch: WebGuard labels web-action risk as SAFE/LOW/HIGH; this project evaluates whether a Moodle action is authorized under roles, platform state and course rules. These are related but different targets.
  • Mapping is consequential: SAFE and LOW are both mapped to ALLOW, while HIGH maps to BLOCK. This deterministic mapping is part of the tested system and may not align with Moodle's permission policy.
  • Fine-tuning details are limited: the PDF shows 2 epochs, batch size 2 and gradient accumulation, but does not provide enough information to independently assess convergence, hyperparameter sensitivity, seed variability or training-set leakage.
  • No error breakdown in the PDF: the printed output gives accuracy, pair accuracy and flip rate, but not false-allow / false-block counts, per-template results, parse-error rates or latency for this new run.
  • Example outputs are illustrative only: the PDF displays one sample from each two-stage model, not a systematic manual audit of all 80 predictions.
  • Do not compare as if conditions were identical: the earlier pilot's Qwen-7B result was 62.5% pair accuracy, while this new run reports 72.5%. This is an observed difference across runs; without controlled seeds, exact code/config comparison and repeated trials, it should not be treated as a statistically established improvement.

Decision gate

The project's working threshold is 80% pair accuracy; the original proposal also treats a very strong full-context baseline near 95% as a reason to reconsider the need for a new gatekeeper.

  • Best new result: Qwen2.5-7B at 72.5% pair accuracy—7.5 percentage points below the 80% gate.
  • Fine-tuned WebGuard: 0% pair accuracy on this task.
  • PolicyGuard-4B: 12.5% pair accuracy on this task.
  • Decision: continue with the research direction, but describe it as a provisional pilot finding. No tested model passes the 80% gate, and the new run does not establish deployment-level reliability.
Bottom lineThe new results strengthen the case for evaluating agent safety with matched context flips rather than item accuracy alone. Qwen-7B is the strongest baseline tested here, but it still misses the project threshold. The fine-tuned WebGuard and PolicyGuard-4B runs are not effective Moodle permission gatekeepers in their current configurations.

Recommended next steps

  1. Generate and retain a complete decision-gate report. Export per-model confusion counts, false allows, false blocks, parse errors, latency, and per-template performance for all six models.
  2. Inspect raw predictions. Sample correct and incorrect cases, especially both halves of each pair, to determine whether errors arise from missing context, prompt interpretation, output parsing or the mapping rules.
  3. Audit the fine-tuning pipeline. Record exact data split, training configuration, random seed, adapter configuration, loss curves and checkpoint provenance. Confirm the Moodle evaluation cases are not present in training data.
  4. Test mappings separately. Compare the current SAFE/LOW/HIGH mapping with alternative explicit decision policies, without silently changing the gold labels.
  5. Improve the dataset. Expand beyond 40 pairs, add new templates and realistic accessibility-tree states, and reduce shortcut cues in titles or wording.
  6. Repeat runs. Evaluate with fixed configurations and multiple seeds where feasible; report uncertainty rather than ranking models from one small run.
  7. Train a task-specific gatekeeper only after the baseline audit. Train directly on the permission decision and its contextual evidence, then compare it against the same baselines using the same matched pairs.
  8. Keep the safety objective asymmetric. Report false allows and false blocks separately. Letting a prohibited action through can have a different cost from blocking a legitimate action.
